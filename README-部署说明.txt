【本次修复 · v111z76｜聊天记录顺序与老卡片重复】
症状：
  ① 以前发的消息跑到最新一条消息旁边（越进房间越多，12 条能变 36 条）；
  ② 往期的特殊卡片（代买 / 查岗 / 红包 / 转账 / KOMO 卡）反复出现在最新消息点。
原因：
  ① 老版本写进历史的行没有 data-created-at，而写盘合并把「缺时间戳」当成 at=0 一律排到
     最末尾；恢复历史 / 翻「更早记录」/ 重绘回执时又给这些行补上 Date.now()，
     于是「磁盘上没有、内存里有」两份身份对不上，每进一次房间就复制一份并挤到最新一端。
  ② 代买卡的历史判定写成「房间在前台就跳过」，卡片落在分页窗口外（>100 行）时 DOM 里
     找不到，就当成没有，在末尾重新补一张。
修复：
  ① 缺时间戳的行改为「沿用左边最近的时间戳原地不动」，不再沉到最后、也不补 Date.now()；
     磁盘与 DOM 两份用「弱身份」兜底合并，不会再复制。
  ② 特殊卡片重建时带上副本记录里的真实时间，按时间插回原来的位置；历史判定不再看前台。
  ③ 进房间时先跑一次幂等修复：把已经损坏的历史去重、老消息挪回时间轴开头。
     跑第二遍不改任何东西，用户数据不会被反复改写。

【本次修复 · v111z77｜老消息 / 老卡片的落位，以及「字体一小步一小步长大」】

v111z76 之后仍然出现的症状：
  ① 以前发的消息仍挤在最新一条消息旁边；进出房间几次之后，同一段老消息会出现好几份；
  ② 往期的特殊卡片（红包 / 转账 / 查岗 / 代买）反复出现在最新的消息点；
  ③ 每切换一次页面，字体就一小步一小步地放大，过一会儿才停。

原因：
  ① 写盘最后一步是 lines.forEach(stampChatMessageLine) —— forEach 会把**数组下标**当成时间戳传进去：
     第 0 行因为下标 0 被当成「正在恢复历史」不补，第 1 行开始每行补上 data-created-at="1"、"2"…
     （等于 1970 年）；于是还没有时间戳的老行 / 老卡片一进房间就被搬到时间轴最前面。
     上一版修复只认「副本缺时间戳」的重复；副本全都带上时间戳之后（每进一次房间都会给它们补一次
     「当时」的时间）就再也认不出来，返回 changed=0，坏数据永远留在原地。
  ② 卡片副本里只剩「09:41」这种没有日期的显示时间时，旧逻辑把它猜成「今天（或昨天）的 09:41」——
     很久以前的卡于是被写上今天的时间戳，直接跳到时间轴最新一端（红包记录的 time 字段正好一直是「HH:MM」）。
  ③ 全局字号是「读一个元素、立刻写它的 font-size」逐个元素做的，还按 7ms 分批：写字号会让整页布局失效，
     下一次 getComputedStyle 又强制整页重排；几千个元素就是几千次重排，于是每切一次页面都要慢慢长大几秒。
     另外调到 100% 时旧实现直接 return，之前写下的内联字号永远撤不掉（调小也回不到原样）。

修复：
  ① 写盘不再发明时间戳：没有 data-created-at 的行保持「没有」，只在显示文案上沿用左边最近一条的时间。
     修复器的快扫补上「整段复制」的指纹：同一段老消息连续 ≥2 行、逐行一字不差、且副本内部相邻时间戳
     只差几毫秒（真人手打不出这种间隔，「TA 嗯 / 你好」来回这种真实重复不会被误伤），进房间即折回 1 份。
     没有时间戳的卡片行也按「时间戳上线前的老行」前移、盖上早于所有真实时间的稳定时间戳
     （KOMO 卡本来就不带时间戳，不动）。
  ② 光一个「09:41」不再猜成今天/昨天：没有 createdAt、显示文案里也没有明确日期（月/日、年/月/日、昨天）
     时一律不作数 —— 卡片保持原位、不再被搬到最新一端；有真实时间（createdAt）的卡片依旧会被纠回正确的行。
  ③ 字号改成「先把要算的元素全部读完，再统一写回」：整棵树一次样式计算 + 一次布局，不再逐格长大；
     已经按当前比例算好的元素直接跳过（切页面几乎零成本）；MutationObserver 把一帧内新加的节点攒成
     一批只扫一次；调回 100% 时把之前写下的内联字号与标记撤掉；写盘时也不再把这些设备字号写进聊天记录。

自测：audit/ 下有 7 个 jsdom 场景脚本（npm i jsdom 后 node audit/scenario1.js …），覆盖
     「老消息不再漂 / 整段复制折回 1 份 / 真实重复不误伤 / 老卡片不再顶在最新点 / 字号幂等」，
     每个脚本都会检查第二遍返回 changed=0（幂等，不会反复改写用户数据）。
